ADR-009 2026-03-12 · ACCEPTED

Mission planner: Behavior Tree + Python

Context

The mission planner must sequence competition tasks (Gate -> Slalom -> Bins -> Octagon), react to events (lost detection, timeout, safety), and stay serviceable across the team's full range of experience levels. The choice covers both the control paradigm (FSM vs Behavior Tree) and the implementation language (Python vs C++).

Options considered
  • Finite State Machine + Python (smach / yasmin)
  • Behavior Tree + Python (py_trees)
  • Behavior Tree + C++ (BehaviorTree.CPP)
  • Custom ROS 2 action scheduler
Decision

Behavior Tree in py_trees (Python), with separate ROS 2 nodes per skill.

Why

Behavior Trees give reactivity without combinatorial state growth (FSM hurts with ~10 tasks × ~5 failure modes). py_trees integrates natively with ROS 2 (py_trees_ros), and the team already knows Python from the perception stack - minimal ramp-up. C++ (BehaviorTree.CPP) would be faster, but the planner is not a hot-path (ticked at 10 Hz), and the context-switch cost between languages in a first-year team would outweigh the gain.

Context

RoboSub consists of ~5 tasks the vehicle executes sequentially. Each task has its own failure modes (lost detections, timeout, low battery). A naive FSM grows combinatorially: every new edge case adds transitions from many states. Behavior Trees instead separate decision (tree structure) from action (leaf nodes), localising changes.

Second axis: Python vs C++. The whole perception stack and tooling is Python. Pixhawk firmware is C, but the planner doesn’t need deterministic real-time - a 10 Hz tick is enough to dispatch high-level actions.

Options considered

OptionProCon
FSM + Python (smach/yasmin)Simple to start, well knownState explosion with many tasks × failure modes, poor reactivity
BT + Python (py_trees)Reactivity, modularity, one language across team, ROS 2 nativeSlower tick than C++ (acceptable)
BT + C++ (BehaviorTree.CPP)Faster, nicer Groot toolingContext switch between languages, steeper learning curve
Custom action schedulerFull controlReinventing the wheel, no ecosystem

Consequences

  • Positive: adding a new task = adding a sub-tree, not rewriting the FSM. Recovery behaviors (e.g. circle-back on lost detection) are reusable as sub-trees across tasks.
  • Acceptable costs: Python GIL overhead is negligible at a 10 Hz tick + all heavy I/O is offloaded to ROS 2 message passing.
  • Migration path: if the planner ever becomes a bottleneck (unlikely), the tree can port to BehaviorTree.CPP - the XML structure is conceptually compatible.
